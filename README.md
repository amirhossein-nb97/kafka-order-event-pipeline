# kafka-order-event-pipeline
A hands-on Data Engineering project demonstrating an event-driven order pipeline with Kafka, FastAPI, and PostgreSQL.
# E-commerce Kafka Event Streaming

An event-driven streaming pipeline for an e-commerce application using **Apache Kafka**.

This project is part of an end-to-end **Data Engineering Platform**. It demonstrates how transactional events generated by an e-commerce application can be published to Kafka and consumed by independent services for analytics and downstream data processing.

| Topic      | Description            |
| ---------- | ---------------------- |

```text
orders
```

# Event Schema

Events are represented as JSON messages.

Example `order_created` event:

```json
{
  "event_id": "8f3a7b12",
  "event_type": "order_created",
  "timestamp": "2026-09-22T10:30:00Z",
  "data": {
    "order_id": 125,
    "customer_id": 42,
    "total_amount": 1500000,
    "currency": "IRR"
  }
}
```

The event contains metadata and business data.

```text
event_id
event_type
timestamp
data
```

# Producers

The producer is responsible for publishing events to Kafka.

Example:

```python
producer.send(
    "orders",
    key=str(order_id),
    value=event
)
```

The order ID is used as the message key.

This allows events belonging to the same order to be consistently routed to the same partition.

# Consumer Groups

Different applications use different consumer groups.

```text
                  Kafka
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   analytics     data-lake   notification
    group          group         group
```

Each consumer group maintains its own offsets.

For example:

```text
orders
   │
   ├── analytics-group
   ├── data-lake-group
   └── notification-group
```

This allows the same event to be independently consumed by multiple applications.

---

# Partitions

Kafka topics are divided into partitions.

Example:

```text
orders
│
├── Partition 0
├── Partition 1
└── Partition 2
```

Messages are distributed across partitions.

Using `order_id` as the message key helps preserve ordering for events belonging to the same order.

```text
order_id = 125
      │
      ▼
Partition 1

order_created
order_updated
order_cancelled
```

---

# Offset

Kafka consumers track their position using offsets.

```text
Partition 0

Offset
  0
  1
  2
  3
  4  ← Consumer
  5
  6
```

If a consumer crashes, it can continue from its committed offset.

# Delivery Semantics

The project explores:

```text
At-most-once
At-least-once
Exactly-once
```

The initial implementation uses **at-least-once delivery** with explicit offset management.

This means a message may be processed more than once, so consumers should be designed to handle duplicate events safely.

# Error Handling

Failed messages can be handled using a retry mechanism.

```text
Kafka
  │
  ▼
Consumer
  │
  ├── Success ──────► Commit Offset
  │
  └── Failure
         │
         ▼
       Retry
         │
         ▼
    Dead Letter Topic
```
